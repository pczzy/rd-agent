# 踩过的坑与防复发清单

记录 2026-08-24 ~ 08-30 期间的实际错误。按**根因模式**归类，每条给出"当时怎么错的 /
怎么被发现的 / 以后怎么防"。

优先看第一节 —— 那几个错误改变过项目结论。

---

## 一、导致结论错误的（最严重）

### 1. 拿两个不同口径的数字直接比较

**错法**：手工测基线时把 label 改成 20 日前瞻收益（`Ref($close,-21)/Ref($close,-1)-1`），
测出 Rank IC 0.0931。但搜索循环用的是模板默认的 1 日 label。之后拿搜索结果
（0.01~0.03）和基线（0.0931）比，得出"搜索结果比基线差 3-7 倍"的错误判断。

**怎么发现**：数字差得太离谱，反查配置才发现两边跑的根本不是同一个任务。

**防**：
- 手工实验若改了任何配置（label / 日期 / 成本 / 股票池），**必须同步检查自动流程是否一致**
- 报告任何"A vs B"的对比前，先确认两者的 label、日期区间、股票池、成本假设完全相同
- 这类错误极隐蔽：两边各自都能跑通、都有合理输出，只有把数字并排才露馅

### 2. 用记忆里的"业界常用值"代替实测校准

**错法**：冲击成本系数取 `c=0.1`，凭"业界常用"的模糊印象。

**实际**：平方根律是 `冲击 = Y × σ_日 × √参与率`，文献 Y ≈ 0.5~1.0。CSI1000 日波动率
2.67%，所以 `c = Y×σ` 应在 **0.013~0.040**。我取的 0.1 隐含 **Y=3.7**，是文献上限的
3.7 倍。

**后果**：这个过悲观的取值直接导致"20 万做不了日频选股"的错误结论。

**防**：
- 任何关键参数，问自己"这个数字是实测的、还是我拍的？"
- 有公式的参数要用**可观测量反推**（这里是用日波动率反推 c），不要直接取经验值
- 参数敏感的结论必须做敏感性分析，并明确标注"结论对 X 敏感"

### 3. 评估时误用了弱信号

**错法**：做 CSI1000 成本分析时，用的是 Alpha20 基线（Rank IC 0.0297），而不是我们
搜出来的 Loop 27 信号（0.0901）。

**怎么发现**：用户直接问"你评估用的loop27?"

**后果**：与错误 #2 叠加，把一个可行方案（净 +7.76%）判成了死路（净 -3.48%）。

**防**：
- 做可行性/成本分析时，**必须用当前最好的信号**，不是随手可得的基线
- 切换数据源或股票池后，SOTA 资产（因子代码、模型）要显式迁移，不能默认还在

> **三个错误的共同教训**：#1、#2、#3 单独存在都不足以翻转结论，叠在一起就把可行方案
> 判成了死路。用户两次追问各揪出一个。**结论越是"意料之外的坏消息"，越要反查前提。**

### 4. 把系统性故障误判成"搜索到瓶颈"

**错法**：观察到 SOTA 连续 15 轮不动，判断"边际收益递减、搜索到瓶颈了"。

**实际**：`np.str_` 列名导致 `combined_factors_df.parquet` 读取失败，**每个 SOTA 因子
实验的回测都在崩溃**，搜索根本没在有效运行。

**防**：
- 下"到瓶颈"这类结论前，先确认**实验确实在成功执行**（有结果产出，不是失败后跳过）
- 区分"跑完了但没提升"和"根本没跑完"

## 二、误读运行状态的（浪费时间，但不改变结论）

### 5. `pgrep -f` 匹配到自己的命令行

**错法**：`pgrep -f "bin/rdagent fin_quant"` 会匹配到执行这条命令的 bash 包装进程，
导致进程明明已停却报告"still running"。**至少犯了 3 次。**

同类：`pkill -f "bin/rdagent fin_quant"` 杀掉了自己的 shell（exit 144），犯了 2 次。

**防**：
```bash
# 错
pgrep -f "bin/rdagent fin_quant"

# 对：用 ps + 精确匹配可执行文件路径，排除 grep 自身
ps -eo pid,cmd | grep -E "envs/rdagent/bin/[^ ]*python[0-9.]* [^ ]*rdagent" | grep -v grep
```

### 6. 日志关键词计数不可信

**错法**：`grep -c "malformed node"` 得到 18、`grep -c "Failed to run"` 得到 9，据此
判断"故障仍在发生"。

**实际**：CoSTEER 把历史失败反馈嵌进**每一次** LLM prompt（这是正确设计，演化式写码
需要看到上一版错在哪），而 `log_llm_chat_content=True` 又把 prompt 全文落盘。过去的
报错因此被反复打印，越往后越多。**误判 2 次。**

**防**：
- 已关闭 `log_llm_chat_content`（`.env`），日志从 17MB 降到约 400KB
- 判断"有没有新故障"只看这两个，不看关键词计数：
```bash
# 1. 服务启动后是否有新的容器执行
find git_ignore_folder/RD-Agent_workspace/*/logs -name 'docker_execution_2*.log' \
     -newermt '2026-08-26 18:48:50'
# 2. 是否有新的结果对象产出
ls -lt pickle_cache/rdagent.scenarios.qlib.developer.*/*.pkl | head
```

### 7. `find -newermt` 用了 systemd 的时间格式

**错法**：`find ... -newermt "$(systemctl show ... ActiveEnterTimestamp --value)"`，
该值形如 `Wed 2026-08-26 18:48:50 CST`，`find` 静默匹配不到任何文件 → 报告"0 次执行"。

**实际**：有 54 次。

**防**：`-newermt` 只用 `'YYYY-MM-DD HH:MM:SS'` 格式，且**结果为 0 时要交叉验证**
（比如 `ls -t` 看最新文件时间戳）。

### 8. 把"父进程 sleep"当成卡死

**错法**：看到主进程状态 `S`（睡眠）、瞬时 CPU 0%，判断"卡住了"。

**实际**：父进程在 `subprocess.check_output` 上等子进程，而**子进程正以 100% CPU 计算**。

**防**：判断卡死要看**整条进程树**：
```bash
ps --ppid <PID> -o pid,stat,%cpu,cmd      # 子进程
py-spy dump --pid <PID>                    # 卡在哪一行
```
另外 `ps` 的 `%cpu` 是生命周期均值，不是瞬时值；瞬时要用 `top -b -n2`。

### 9. 管道阻塞造成的假超时

**错法**：`git push ... | tail -2` 超时退出（exit 143），以为推送失败。

**实际**：推送成功了，是长输出写入管道时阻塞。

**防**：长时间命令**重定向到文件**再读，不要直接管道给 `head`/`tail`：
```bash
timeout 300 git push origin main > /tmp/push.log 2>&1; echo "exit=$?"; tail -3 /tmp/push.log
```

## 三、验证方式无效的

### 10. 冒烟测试没有覆盖真正会失败的代码路径

**错法**：给 systemd 定时任务写好启动脚本后，用 `rdagent fin_quant --help` 做冒烟测试，
通过了就认为没问题。

**实际**：18:00 定时触发，13 秒后失败 —— `CONDA_DEFAULT_ENV` 在 systemd 环境下不存在，
`CondaConf` 校验失败。`--help` 根本走不到那段代码。

**防**：
- 冒烟测试要**跑到真正会用到环境的那一步**，不能只验证入口能解析参数
- 交互式 shell 里能跑通 ≠ systemd/cron 下能跑通。非交互环境缺少：
  `CONDA_DEFAULT_ENV`、`CONDA_PREFIX`、`PATH` 里的 `condabin`、各种 shell profile 导出的变量
- 已加固：`factor_coder/config.py` 在该变量缺失时从 `sys.prefix` 推导

### 11. 假设 API 的语义而不去读代码

**错法**：以为 `hold_thresh`（最短持有天数）能降低换手 → 实测换手几乎没降，收益反而变差。
以为"定期全量调仓"能降换手 → 换手不降反升（单次全量重排的换手比每天换 1 只还高）。

**防**：
- 改策略参数前先读该参数的实现，确认它作用在哪个环节
- 换手是 `单次换手 × 调仓频次`，**只改一个因子可能被另一个抵消**

## 四、工具与命令细节

### 12. typer 把下划线转成连字符

`--loop_n` 报 `No such option`，正确是 `--loop-n`。注意 `quant.py` docstring 里写的
`--step_n` 是**直接调用 python 模块**时的写法，走 CLI 要用连字符。

### 13. `--loop-n` 是总数，不是剩余数

续跑时 `loop_idx` 被重置为 0（`utils/workflow/loop.py:375`），`kickoff_loop` 会为
**每一个已完成的 loop 也扣减一次** `loop_n`。而且 `loop_n` 会从 pickle 恢复上次的残留值。

- 要到达 loop N，传 `--loop-n (N+1)`
- `loop.py:132` 那句 `# remain loop count` 注释是误导的
- **犯过 2 次**：一次传 6 只跑了 1 轮，一次不传导致加载后 `loop_n=3` 只跑了 3 个 loop 就退出

### 14. qlib 的 `$close` 是复权价

真实市价 = `$close / $factor`。用复权价算出的"一手成本"严重偏低：CSI300 中位数算成
558 元，真实是 **2478 元**（差 4.4 倍）。

验证方法：取茅台/工行等已知股票，看 `$close/$factor` 是否接近真实价位。

### 15. 新建 git 仓库时的两个陷阱

- **`.git` 备份成普通目录后会被 `git add -A` 收进去**：69MB 的 pack 文件差点提交。
  备份要移到**仓库目录之外**。
- **`.gitignore` 的 `.env*` 会连 `.env.example` 一起忽略**：旧仓库里它是已跟踪文件所以
  不受影响，新仓库要 `git add -f` 加回。
- 提交前必查：`git diff --cached --name-only | grep -E "^\.env"` 以及扫描 `sk-` 开头的
  真实密钥。

## 五、通用检查清单

下结论前过一遍：

- [ ] 这个数字是**实测**的，还是我**取的经验值**？取的话有没有可观测量能反推？
- [ ] 对比的两组，label / 日期 / 股票池 / 成本假设**是否完全一致**？
- [ ] 用的是**当前最好的信号**，还是随手可得的基线？
- [ ] "没提升"是真没提升，还是**实验根本没跑成功**？
- [ ] 进程状态判断有没有**匹配到自己的命令行**？
- [ ] 日志里的报错是**新发生的**，还是历史内容被回显？
- [ ] 结论是"意料之外的坏消息"吗？如果是，**反查前提**。

排查故障时，可靠的证据来源排序：

1. 文件时间戳（新产生的容器日志、结果对象）
2. `py-spy dump` 看真实调用栈
3. 在容器里手工复现，拿完整堆栈
4. ~~日志关键词计数~~（不可信）
